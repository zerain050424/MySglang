# RR-EVICT vs T-LRU：burst/pause 场景对比结果

> 场景：**小流量持续涌入，把长挂起会话的 KV 挤掉**，随后这些会话同时/分批回归。
> 结论：**RR-EVICT 在 resume 维度全面胜出（+18 ~ +44 pt），T-LRU（插件形态与原生形态）在本场景
> 22k 预算下无任何保护作用。**

本文件沉淀：数据集设计、实验方案、三轮参数标定、结果表、机理证据、复现命令、已知局限。

---

## 1. 摘要

| 问题 | 答案 | 证据强度 |
|---|---|---|
| RR-EVICT 能否保住长挂起会话？ | **能**，resume 命中率 6 % → 50 %（22k）/ 75 %（30k） | 强（2 seed × 2 预算 × 2 模式，同号） |
| T-LRU（插件形态）能否？ | **不能**，与对照逐位相同（6.14 / 6.17） | 强 |
| T-LRU（原生 unified 形态）能否？ | **22k 下不能**（6.14，三档阈值相同）；30k 下部分（38–40 %） | 中（机理待探针确认） |
| T-LRU 调参后的理论上限？ | **22k 下 25 %、30k 下 56 %**（§6.2 的结构性夹逼，与阈值无关） | 强（模型 + 30k 实测落在预测内） |
| RR 有代价吗？ | 22k 下用 1–2 pt 全局命中率换 44 pt 尾部保护；30k 下**全面占优**（无权衡） | 强 |
| 同时回归 vs 分批回归？ | 同时更伤尾部 TTFT（p99 253 vs 159 ms），但**分批会把 RR 的优势从 50 pt 压到 24 pt** | 强 |

## 2. 数据集设计

### 2.1 两个角色

| 角色 | 数据 | 配置 | 作用 |
|---|---|---|---|
| **victim**（长挂起） | `AgentBank_alfred_scale_5000_session_data.jsonl`（多轮 agentic） | `max_record: 8`，`max_turns: 12`，`pause_after_turn: 3`，`arrival.mode: fixed`（step 0.05 s） | 同相位起跑 → 第 3 轮后挂起 → 等 burst 窗口结束再回归 |
| **搅拌**（小流量） | `AgentBank_apps_session_data.jsonl`（单轮，短请求） | `max_record: 70`，`lambda_rate: 1.2`，`gate_after: true` | 全部 victim 挂起后才开始涌入，持续 60 s |

三处设计要点：

1. **victim 必须同相位**：Poisson 到达会把 pause 点打散，`arrival.mode=fixed` 才能让 8 个 victim
   几乎同时挂起（实测全部在 5.0–6.0 s 越过 pause 点）。
2. **搅拌必须等 victim 全部挂起**：`gate_after: true` 由 `BurstGate` 控制，保证淘汰压力只落在
   pause 窗口内，而不是和 victim 起跑阶段混在一起。
3. **victim 不能设 `gate_after`**：那会让它等待「自己挂起后才会置位」的屏障 → 死锁（实测踩过）。

## 3. 实验方案

### 3.1 四个臂

| 臂 | 后端 | 配置 | 说明 |
|---|---|---|---|

### 3.2 `force_agentic`：为什么必须开

不开的话，插件拿不到流量（详见 `README.md` 与历史分析）：

| 机制 | 不开 | 开了 |
|---|---|---|
| 新节点标签 | `QTRANS` → `is_one_shot=True` → **被 one-shot 硬优先带先清** | `QAGENT` |
| 命中后标签 | 间隔 < 8 s 才 `QAGENT`，否则 `QCHAT`（插件作用域之外） | 恒 `QAGENT` |
| 分叉父节点 | 无条件 `QSTRUCT`（走位置项评分，深处 clamp 到 0） | 跳过 |
| 插件覆盖率 | 实测 ~60 %（由 8 s 阈值决定） | 100 % |

实现只改 `queue_tag`，**不动 `session_type`**，分类器自身的统计仍然可测。

### 3.3 burst / pause 时序与两种回归方式

```
t0        victim 同相位起跑（fixed arrival，step 0.05 s），跑 3 轮
t_pause   8 个 victim 全部越过 pause 点 → BurstGate 放行搅拌流
          ── burst 窗口 60 s：70 条 apps 单轮请求以 λ=1.2/s 涌入 ──
t_open    窗口关闭 → ResumeGate 放行 victim：
            simultaneous  8 个同时恢复（thundering herd）
            batched       victim i 在 t_open + (i // 4) × 10 s 恢复
t_tail    victim 跑完剩余 9 轮
```

新增的 CLI：`--burst-duration-s` / `--resume-mode` / `--resume-wave-size` /
`--resume-wave-interval-s`；服务端记录 `phases{burst_start_s, burst_end_s, victim_resumed_s}`，
逐请求 CSV 新增 `resume_phase` 列（`pre` / `pause` / `resume` / `post`）。

### 3.4 压力标定：三轮教训（本实验最关键的一节）

T-LRU / RR 的差异只在「压力刚好够、但不至于碾平一切」的窗口里出现。前两轮都调错了：

| 轮次 | 搅拌规模 | 预算 | 实测结果 | 归档 |
|---|---|---|---|---|
| ① 压力过大 | 300 × λ6 ≈ 360k tokens | 60k | 需求 = 预算的 **6×** → 三臂 resume 全为 6.17 / 6.14，策略无法介入 | `result_saturated_6x/`（24 点） |
| ② 压力为零 | 70 × λ1.2 ≈ 27k tokens | 60k / 100k | 常驻仅 **35.7k < 60k** → `victim_src` 一行未打印，**零淘汰** | `result_no_eviction_60k_100k/`（12 点） |
| ③ 可用区间 | 70 × λ1.2（不变） | **22k / 30k** | 1.62× / 1.19× → 常驻填满（pool_max 21,737）、策略决定 84 % 的淘汰 | 本轮结果 |

结论一句话：**压力杠杆是「预算」，不是「搅拌流量」**。搅拌加到 3 倍只会把相对压力推到 0。

### 3.5 矩阵与耗时

3 臂 × 2 回归方式 × 2 预算 × 2 seed = **24 次**（原生 TLRU 另加 8 + 4 次）。

## 5. T-LRU 的原理与源代码实现

### 5.1 原理

T-LRU（Tail-Optimized LRU，arXiv:2510.15152）针对的是**单条会话的尾部冗余**：
一条历史长度为 `L` 的对话，下一轮 prompt 只会新增 `Q_hat` 个 token，因此要让下一次 prefill
落在 TTFT 预算内，只需保证前 `budget` 个 token 驻留即可：

```
budget = max(L + Q_hat − threshold, 0)
```

起点已经越过 `budget` 的片段，对下一轮的 prefill 已无贡献（论文称 **TEL-safe**，
Tail-Eviction-Lossless），可以最先淘汰。实现上它不新增淘汰器，而是把这类节点报成
「无限旧」，借用现有驱动实现两阶段：

| 阶段 | 判据 | 顺序 |
|---|---|---|
| phase 1 | `tel_safe == True` | 先清空所有 TEL-safe 的尾巴 |
| phase 2 | TEL-safe 用尽 | 回到纯 recency（LRU） |

`threshold` 是「TTFT 预算能容忍的驻留量」，`Q_hat` 是下一轮预计新增量。二者都是 token 数
（论文以 block 计，移植需乘 `page_size`）。

关键在于：**它只止损单条会话的尾部，不涉及会话之间该由谁让步**。这一点是后面所有结论的根源。

### 5.2 核心实现：只有一个 20 行的优先级函数

`python/sglang/srt/mem_cache/evict_policy.py:79-114`

```python
class TLRUStrategy(EvictionStrategy):
    def __init__(self, threshold: int = 0, next_prompt_estimate: int = 0):
        self.threshold = threshold
        self.next_prompt_estimate = next_prompt_estimate

    def get_priority(self, node) -> Tuple[int, float]:
        # node._tlru_history_len 是分支高水位（论文的 L），裁尾时刻意不回退。
        # 若改用「当前驻留深度」当 L，被裁过尾的会话会永远觉得自己超额，
        # T-LRU 会一路把它削到 0，而不是停在 (threshold - Q_hat)。
        budget = max(
            node._tlru_history_len + self.next_prompt_estimate - self.threshold, 0
        )
        cached_without_this_node = node._tlru_cached_prefix_len - len(node.key)
        tel_safe = cached_without_this_node >= budget
        return (-1 if tel_safe else 0, node.last_access_time)
```

三个字段的语义：

| 字段 | 含义 | 量纲 |
|---|---|---|
| `_tlru_cached_prefix_len` | 从根到**本节点末尾**的累计 token 数 | token |
| `len(node.key)` | 本片段长度 | token |
| 二者差 | 本节点**起始**处的绝对偏移 | token |
| `_tlru_history_len` | 本节点**子树曾到过的最大深度**（即 L） | token |

### 5.3 记账：两个字段如何被维护

字段定义在 `unified_cache/unified_tree_core.py:132-133`，默认 0：

```python
self._tlru_cached_prefix_len = 0   # tokens root -> self
self._tlru_history_len = 0         # branch high-water
```

唯一维护函数（`:189-207`），在**节点创建时**调用：

```python
def _set_tlru_lens_and_raise_history(node, parent) -> None:
    node._tlru_cached_prefix_len = parent._tlru_cached_prefix_len + len(node.key)
    if node._tlru_history_len < node._tlru_cached_prefix_len:
        node._tlru_history_len = node._tlru_cached_prefix_len
    cur = parent
    while cur is not None and cur._tlru_history_len < node._tlru_cached_prefix_len:
        cur._tlru_history_len = node._tlru_cached_prefix_len   # 沿祖先链上抬
        cur = cur.parent
```

三个刻意的设计：

1. **单调不减**：高水位不随裁剪下降，否则会话会陷入「越裁越觉得自己超额」的自毁循环；
2. **向祖先传播**：一条链最深处的深度会抬升其所有祖先 ⇒ `L` 是「子树历史最大深度」，不是「本会话长度」；
3. **分裂继承**（`:1381-1390`）：`new_node._tlru_history_len = child._tlru_history_len`——
   分裂不增加分支深度。

调用点只有三处，全部由策略名门控（`:439-441`）：

```python
self.tlru_bookkeeping = params.eviction_policy.lower() == "tlru"
```

| 场景 | 位置 |
|---|---|
| 新尾巴插入 | `:1448`（device）、`:2202`（host 回填） |
| 节点分裂 | `:1381-1390` |
| 其他策略 | 跳过，字段恒 0 |

### 5.4 消费者：复用的 FULL 组件堆

TLRU 没有自己的淘汰循环，优先级由 `unified_cache/components/full.py` 的堆驱动消费：

```python
# :190-193  堆键 = (是否被会话引用, 引用数, TLRU 优先级)
def _session_ref_eviction_strategy(self, node):
    ref = self.session_ref(node)
    return ref > 0, ref, self.tree_core.eviction_strategy.get_priority(node)

# :196-203  每个淘汰批次开头建堆（覆盖当前所有可淘汰 device 叶子）
self._evict_device_heap = [
    (self.session_ref_eviction_strategy(n), n)
    for n in self.tree_core.evictable_device_leaves
]
heapq.heapify(self._evict_device_heap)

# :205-236  每步弹一个；被弹节点的父节点若变成叶子则回灌
while tracker[ct] < self._evict_device_request_cnt and self._evict_device_heap:
    _, x = heapq.heappop(self._evict_device_heap)
    if x not in self.tree_core.evictable_device_leaves:
        continue          # 陈旧条目
    self._evict_device_last_node = x
    return x.id
```

`enable_session_radix_cache` 默认关闭 ⇒ `ref = 0` ⇒ 堆键退化为纯 TLRU 优先级。
数量级上的代价是：每批淘汰 `heapify` O(N)；每次插入沿祖先上抬 O(路径节点数)。

### 5.5 启动与退化条件（两条硬校验）



因此原生 TLRU 的启动形态是**两个参数都必填**：

```bash

--radix-eviction-policy-config '{"threshold": 320, "next_prompt_estimate": 71}'
```

两处退化端点（都在本实验里真实出现过或逼近过）：

| 条件 | 后果 |
|---|---|
| `threshold ≤ Q_hat` | `budget > L` ⇒ 无节点 TEL-safe ⇒ 纯 LRU（启动校验直接拦住） |
| `threshold ≥ max(L) + Q_hat` | `budget = 0` ⇒ **全部** TEL-safe ⇒ 同档内按 `last_access_time` = 纯 LRU |

## 6. 表现不佳的原因

分四层，从结构性到实现层，证据强度递减。

### 6.1 语义错配（结构性，与实现无关）

本场景的伤害机制是**跨会话资源竞争**：小流量（70 条一次性会话）在 60 s 内把缓存填满，
需要挤掉 13.7k token，而长挂起会话的链是最老的、必然首当其冲。

T-LRU 的优化目标是**单条会话的尾部冗余**，它的判据是逐节点的
`cached_without_this_node >= budget`，只回答「这个节点的起点够不够深」。它无法表达：

- 「这条会话 65 s 后要回归，别一次抽干它」——没有会话概念；
- 「每条会话最多只能被削 50 %」——RR 的 `loss_cap(L)` 是**会话级配额**，T-LRU 没有对应的量纲；
- 「该让谁让步」——T-LRU 只能决定「先删深度最大的」，无法在会话之间做取舍。

在 T-LRU 眼里，一条即将回归的活跃会话的尾巴，与一条已经死掉的会话的尾巴完全相同。
本实验里 RR 拿到 50–75 %、T-LRU 只有 6 %，根源就在这里。

### 6.2 结构性夹逼：调参无法突破的上限（可定量）

`budget` 是一个**全局标量**，却要同时满足两个互相冲突的要求：

**要求 ①（保护）**：想让 victim 保留前 `P` 个 token ⇒ `budget ≥ P` ⇒ `threshold ≤ L_v + Q − P`

**要求 ②（供给）**：淘汰量 `D` 只能从 TEL-safe 的尾巴里出，否则落入 LRU 阶段（最老的 victim 先死）
⇒ 每条搅拌会话贡献 `L_s − budget_s = threshold − Q` 个可淘汰 token
⇒ `N_stir × (threshold − Q) ≥ D` ⇒ `threshold ≥ Q + D / N_stir`

把 ① 与 ② 联立，得到**保护上限**：

```
P_max = L_v − D / N_stir
```

本实验的实测参数：`L_v = 290`（挂起点链长）、`N_stir = 70`、`D = 35.7k − budget`：

| 预算 | D | `P_max` | resume 命中率上限 `P_max/376` | 实测 |
|---|---|---|---|---|
| 22k | 13.7k | 290 − 196 = **94** | **25 %** | 6.14 %（阈值 90/200/320 均未落在最优点 267） |
| 30k | 5.7k | 290 − 81 = **209** | **56 %** | 37.8 % / 39.6 %（落在上限内 ✅） |

这个模型同时解释了之前三轮参数标定的全部现象：

| 轮次 | D | `P_max = L_v − D/N_stir` | 预期 |
|---|---|---|---|
| ① 6× 饱和（60k 预算、360k 需求） | 极大 | **< 0** | 完全零保护 ⇒ 三臂必然相同 ✅ 实测正是如此 |
| ② 零淘汰（60k 预算、35.7k 需求） | 0 | 290 | 无需保护（也没有淘汰） ✅ |
| ③ 22k | 13.7k | 94 | ≤ 25 % |
| ③ 30k | 5.7k | 209 | ≤ 56 % |

也就是说：**在 22k 下，无论 `threshold` 怎么调，T-LRU 的 resume 命中率都不可能超过 25 %；
而 RR 达到 50 %。** 30k 下 T-LRU 能到 38–40 % 也在模型预测的 56 % 上限之内，
说明这个夹逼模型是自洽的——它不是「参数没调好」，而是**机制本身没有足够的自由度**。

对照 RR：`loss_cap(L) = min(kappa·L, L − max(512, 0.3L))` 是**随 L 缩放**的会话级配额，
再加上「跨会话挑最久未被服务者」的选择权，因此不受这个夹逼约束。

### 6.3 参数标定错误（本实验实际踩到过）

插件形态（A2）用 `threshold = 943`，是按会话**最终长度** p50 = 1124 标定的；
但 victim 在第 3 轮挂起，链长只有 **290**：

```
budget = max(290 + 71 − 943, 0) = 0 ⇒ 全部 TEL-safe ⇒ 纯 LRU
```

正确做法是按**挂起点长度**标定，且目标不是「保护整条链」而是 §6.2 的最优点
（22k 下约 267）。这也解释了为什么第一次重标到 320 仍然失败——320 给出 `P = 41`，
只保住了 41 个 token。

### 6.4 实现层：一处尚未定论的偏差

`threshold ∈ {90, 200, 320}` 三档在 22k 下给出**完全相同**的 `resume_hit = 6.14 %` 与
`recompute = 2935`。按 §6.2 的模型，三档应分别保护 271 / 161 / 41 个 token，不可能同值。

两种解释，目前**未区分**：

| 解释 | 机制 | 支持证据 | 反对证据 |
|---|---|---|---|
| **A. 记账缺失** | 被淘汰叶子的 `_tlru_history_len` 仍为 0 ⇒ `budget` 恒为 0 ⇒ 全 TEL-safe ⇒ LRU | 三档同值；6.14 % 正好等于「只剩共享前缀」 | 30k 下 T-LRU 明显优于对照（37.8 % vs 6.14 %），若恒为 LRU 不应有差异 |
| **B. TEL-safe 池不足** | `P` 并非上限，而是「池够用时才能保住」，池不够则转 LRU | 阈值 90 / 200 的池分别只有 1.5k / 10k，都小于 `D = 13.7k`，确实会退回 LRU | 阈值 320 的池 ≈ 19.4k > 13.7k，按模型应保护 41 token（≈11 %），实测只有 6.14 % |

两者共同指向同一个待测数据：**22k 下 `_tlru_history_len` 的实际取值，以及 TEL-safe 判定
在每个节点上的分布**。定位方法（约 10 分钟）：

```python
# evict_policy.py::TLRUStrategy.get_priority 临时插入（env 门控，跑完即 revert）
if os.environ.get("SGLANG_TLRU_DEBUG") == "1" and _dbg.n < 100:
    _dbg.n += 1
    logger.warning("[tlru] L=%d budget=%d cw=%d tel_safe=%s",
                   node._tlru_history_len, budget, cached_without_this_node, tel_safe)
```

判读：`L` 全为 0 → 解释 A（记账问题，属于 sglang 侧的缺陷）；
`L ≈ 290` 且 `tel_safe` 有 True/False 之分 → 解释 B（机制上限，与 §6.2 一致）。

### 6.5 小结：三层原因的重要性排序

| 层次 | 原因 | 能否通过调参解决 | 证据强度 |
|---|---|---|---|
| 1 | **语义错配**：无会话概念，只有节点深度 + 时间 | ❌ 不能 | 强（RR 同环境 50–75 % vs 6 %） |
| 2 | **结构性夹逼**：22k 下 `P_max = 94`，上限 25 % | ❌ 不能 | 强（模型 + 30k 实测落在预测内） |
| 3 | 参数标定（按 1124 而非 290 标） | ✅ 能，但只能吃到第 2 层的上限 | 强（插件形态 threshold=943 的 budget=0） |
| 4 | 实现层偏差（三档同值） | 未知，需探针 | 弱（两种解释均有反证） |

**结论**：T-LRU 打不过 RR-EVICT 的主因是第 1、2 层——它优化的是「单会话尾部冗余」，
而本场景的伤害来自「跨会话资源竞争」；即便把参数调到理论最优，22k 下的上限也只有 25 %，
仍不到 RR 的一半。

## 8. 局限

1. **只有 2 个 seed**（为压缩时长），配对差同号是必要条件但样本偏小；3 seed 需 +24 min。
2. **RR 的 resume 明细 CSV 已丢失**：上一轮启动原生实验前误执行 `rm -rf result`，RR 的 resume 数字
   取自当时 `summarize.py` 的输出（2-seed 中位数）。全局指标已从 tmux 回滚缓冲恢复到
   `result_recovered_22k_30k/`。若要可复算的 RR CSV，需重跑 47 min。
3. **原生 TLRU 的 22k 退化机理未定**（§6.4），因此「TLRU 不行」的具体机制目前只能限定在
   「threshold ∈ {90, 200, 320} 且 22k 预算」这一范围；但 §6.1/6.2 的结构性结论不依赖它。
4. 负载是单一 agentic 数据集；混合负载（chat/struct 并存）下 `force_agentic` 会改变评分口径，
   结论不可直接外推。
5. 22k 预算下池容量小，高并发时可能出现请求级抢占（而非纯缓存淘汰），本轮未单独度量。
