# RR-EVICT vs T-LRU：burst/pause 场景对比结果

> 场景：**小流量持续涌入，把长挂起会话的 KV 挤掉**，随后这些会话同时/分批回归。
> 结论：**RR-EVICT 在 resume 维度全面胜出（+18 ~ +44 pt），T-LRU（插件形态与原生形态）在本场景
> 22k 预算下无任何保护作用。**

本文件沉淀：数据集设计、实验方案、三轮参数标定、结果表、机理证据、复现命令、已知局限。

---

## 1. 摘要

| 问题 | 答案 | 证据强度 |
|---|---|---|
| RR-EVICT 能否保住长挂起会话？ | **能**，resume 命中率 6 % → 50 %（22k）/ 75 %（30k） | 强（2 seed × 2 预算 × 2 模式，同号） |
| T-LRU（插件形态）能否？ | **不能**，与对照逐位相同（6.14 / 6.17） | 强 |
| T-LRU（原生 unified 形态）能否？ | **22k 下不能**（6.14，三档阈值相同）；30k 下部分（38–40 %） | 中（机理待探针确认） |
| RR 有代价吗？ | 22k 下用 1–2 pt 全局命中率换 44 pt 尾部保护；30k 下**全面占优**（无权衡） | 强 |
| 同时回归 vs 分批回归？ | 同时更伤尾部 TTFT（p99 253 vs 159 ms），但**分批会把 RR 的优势从 50 pt 压到 24 pt** | 强 |

## 2. 数据集设计

### 2.1 两个角色

| 角色 | 数据 | 配置 | 作用 |
|---|---|---|---|
| **victim**（长挂起） | `AgentBank_alfred_scale_5000_session_data.jsonl`（多轮 agentic） | `max_record: 8`，`max_turns: 12`，`pause_after_turn: 3`，`arrival.mode: fixed`（step 0.05 s） | 同相位起跑 → 第 3 轮后挂起 → 等 burst 窗口结束再回归 |
| **搅拌**（小流量） | `AgentBank_apps_session_data.jsonl`（单轮，短请求） | `max_record: 70`，`lambda_rate: 1.2`，`gate_after: true` | 全部 victim 挂起后才开始涌入，持续 60 s |

三处设计要点：

1. **victim 必须同相位**：Poisson 到达会把 pause 点打散，`arrival.mode=fixed` 才能让 8 个 victim
   几乎同时挂起（实测全部在 5.0–6.0 s 越过 pause 点）。
2. **搅拌必须等 victim 全部挂起**：`gate_after: true` 由 `BurstGate` 控制，保证淘汰压力只落在
   pause 窗口内，而不是和 victim 起跑阶段混在一起。
3. **victim 不能设 `gate_after`**：那会让它等待「自己挂起后才会置位」的屏障 → 死锁（实测踩过）。

### 2.2 实测画像

原始 alfred 数据：3358 个 session，**轮数 p50 = 35、mean = 40、max = 161** —— 直接跑会得到
单次 30 分钟以上的 run，且 pause 点漂移。因此截断到 **12 轮**（对齐早期 RR 实验的规模）。

每轮 prompt 长度（全量 3358 session 实测，token）：

| turn | p50 | mean | p90 | 说明 |
|---|---|---|---|---|
| 1 | 126 | 150 | 221 | |
| **3** | **290** | 339 | 505 | **挂起点**（决定 T-LRU 的 `L`） |
| **4** | **376** | 432 | 636 | **回归点**（resume 的分母） |
| 12 | 1124 | 1220 | 1672 | 会话最终长度（T-LRU 阈值若按这个标定会严重偏大） |

单次 run（166 请求）实测：

| 任务 | 请求 | prompt tokens | 每条均值 | 命中率 |
|---|---|---|---|---|
| agentic_idle（victim） | 96 | 57,535 | 599 | 84.4 % |
| agentic_active（搅拌） | 70 | 27,111 | **387** | 6.4 % |
| 合计 | 166 | 84,646 | — | 59.4 % |

**全树常驻峰值 35.7k tokens**（预算 60k 时从未填满）。这个数是后面所有预算标定的基准。

## 3. 实验方案

### 3.1 四个臂

| 臂 | 后端 | 配置 | 说明 |
|---|---|---|---|
| `a0_control` | simple_hybrid | `{"force_agentic": true}` | 纯全局 `victim_key`（alpha × lognormal），无插件 |
| `a1_rr` | simple_hybrid | `+ rr.fair_rr=true, kappa=0.5, retain=512/0.3` | 会话轮询 + 单会话配额 `loss_cap(L)` |
| `a2_tlru` | simple_hybrid | `+ tlru.enabled, threshold=943, Q=71` | T-LRU 公式做成**插件**（只修 QAGENT 候选） |
| `a3_native_tlru` | **unified** | `+ threshold/Q`（原生 `--radix-eviction-policy tlru`） | 仓库原生 TLRU，全局排序 |
| `a4/a5_tlru_t90/t200` | unified | 阈值敏感性 | 仅 22k / simultaneous / 2 seed |

### 3.2 `force_agentic`：为什么必须开

不开的话，插件拿不到流量（详见 `README.md` 与历史分析）：

| 机制 | 不开 | 开了 |
|---|---|---|
| 新节点标签 | `QTRANS` → `is_one_shot=True` → **被 one-shot 硬优先带先清** | `QAGENT` |
| 命中后标签 | 间隔 < 8 s 才 `QAGENT`，否则 `QCHAT`（插件作用域之外） | 恒 `QAGENT` |
| 分叉父节点 | 无条件 `QSTRUCT`（走位置项评分，深处 clamp 到 0） | 跳过 |
| 插件覆盖率 | 实测 ~60 %（由 8 s 阈值决定） | 100 % |

实现只改 `queue_tag`，**不动 `session_type`**，分类器自身的统计仍然可测。

### 3.3 burst / pause 时序与两种回归方式

```
t0        victim 同相位起跑（fixed arrival，step 0.05 s），跑 3 轮
t_pause   8 个 victim 全部越过 pause 点 → BurstGate 放行搅拌流
          ── burst 窗口 60 s：70 条 apps 单轮请求以 λ=1.2/s 涌入 ──
t_open    窗口关闭 → ResumeGate 放行 victim：
            simultaneous  8 个同时恢复（thundering herd）
            batched       victim i 在 t_open + (i // 4) × 10 s 恢复
t_tail    victim 跑完剩余 9 轮
```

新增的 CLI：`--burst-duration-s` / `--resume-mode` / `--resume-wave-size` /
`--resume-wave-interval-s`；服务端记录 `phases{burst_start_s, burst_end_s, victim_resumed_s}`，
逐请求 CSV 新增 `resume_phase` 列（`pre` / `pause` / `resume` / `post`）。

### 3.4 压力标定：三轮教训（本实验最关键的一节）

T-LRU / RR 的差异只在「压力刚好够、但不至于碾平一切」的窗口里出现。前两轮都调错了：

| 轮次 | 搅拌规模 | 预算 | 实测结果 | 归档 |
|---|---|---|---|---|
| ① 压力过大 | 300 × λ6 ≈ 360k tokens | 60k | 需求 = 预算的 **6×** → 三臂 resume 全为 6.17 / 6.14，策略无法介入 | `result_saturated_6x/`（24 点） |
| ② 压力为零 | 70 × λ1.2 ≈ 27k tokens | 60k / 100k | 常驻仅 **35.7k < 60k** → `victim_src` 一行未打印，**零淘汰** | `result_no_eviction_60k_100k/`（12 点） |
| ③ 可用区间 | 70 × λ1.2（不变） | **22k / 30k** | 1.62× / 1.19× → 常驻填满（pool_max 21,737）、策略决定 84 % 的淘汰 | 本轮结果 |

结论一句话：**压力杠杆是「预算」，不是「搅拌流量」**。搅拌加到 3 倍只会把相对压力推到 0。

### 3.5 矩阵与耗时

3 臂 × 2 回归方式 × 2 预算 × 2 seed = **24 次**（原生 TLRU 另加 8 + 4 次）。

| 项 | 单次 |
|---|---|
| server 启动 | ~90 s（最大固定开销） |
| bench（166 请求 + 60 s burst 窗口） | 75–84 s |
| `/flush_cache` | ~2 s |

`run_matrix.sh` 按 `(arm, budget)` **复用 server**（只依赖这两个轴），seed 之间用 `/flush_cache`
隔离；24 次运行只启动 6 次，实测 **47 分钟**跑完。

### 3.6 指标与判据

主指标是 **resume 轮**（挂起后第一个回归请求，`resume_phase == "resume"`）：

| 指标 | 含义 |
|---|---|
| `resume_hit_pct` | Σcached / Σprompt（仅 resume 轮） |
| `resume_recompute` | resume 轮重算 token 总量 |
| `resume_ttft_p99` | resume 轮 TTFT 尾部 |
| 全局 `cache_hit_rate_pct` / `ttft_p99` | 保护尾部的代价 |

判据（跑前写死）：同 `(seed, budget)` 配对差值；2 seed 同号才算结论；|Δ| < 1 pt 视为持平。

### 3.7 有效性检查（每轮必看）

| 检查 | 门槛 | 本轮实测 |
|---|---|---|
| 淘汰真的发生 | `pool_max ≈ budget` | 21,737 / 22,000 ✅ |
| 策略真的接管 | `victim_src` 里 `qagent` 占比 | RR 臂 12,641 / 15,090 = **84 %** ✅ |
| one-shot 未被抢先 | `one_shot_evicted=0` | ✅ |
| 相位完整 | 8 个 `victim_resumed_s` + burst 窗口 ≈ 60 s | ✅ |
| seed 确定性 | seed 42 vs 43 差 | ≤ 0.03 pt ✅ |

### 4.4 保护尾部的代价：全局指标

| 臂 | 22k 全局 hit% | 22k 全局 p99 | 30k 全局 hit% | 30k 全局 p99 |
|---|---|---|---|---|
| A0 对照 | 57.92 / 57.94 | 233.6 / 157.6 | 57.97 / 57.93 | 270.8 / 166.2 |
| **A1 RR** | 52.69 / 56.01 | **171.6** / 151.6 | **60.48 / 60.49** | **124.3 / 127.2** |
| A2 T-LRU（插件） | 57.95 / 57.96 | 273.1 / 158.1 | 57.95 / 57.98 | 242.9 / 158.2 |
| A3 T-LRU（原生） | 54.70 / 57.13 | 252.8 / 158.7 | 56.68 / 58.09 | 192.2 / 125.6 |

（单元格为 同时 / 分批）

两个要点：

- **22k 是权衡**：RR 用 −2.0 pt 全局命中率（52.69 vs 54.70）换 +44 pt resume 命中率；
- **30k 无权衡**：RR 的全局命中率反而比对照高 2.5 pt（60.48 vs 57.97），resume 又高 69 pt ——
  说明压力适中时「保护活跃会话」与「总命中率」并不冲突。

### 4.5 同时回归 vs 分批回归

| 观察 | 数据 |
|---|---|
| 分批把尾部 TTFT 摊平 | 对照 22k：284.5 → 159.5 ms（−44 %） |
| 分批同时削弱 RR 的保护 | RR 22k：50.21 → 24.11 pt（**−26 pt**） |
| 30k 下两者趋同 | RR：75.41 = 75.41 |

机理：分批回归时，先恢复的 4 个 victim 立刻继续跑后续 9 轮（每轮 ~600 token），把 22k 缓存
重新填满，**在第二批恢复之前就把它们的链挤掉了**。所以「分批」不是免费的好事。

## 5. 分析与讨论

### 5.1 RR 为什么有效

两个机制叠加：

1. **会话级轮询**：`_pick_round_robin` 在每个会话上取最深叶子，跨会话挑「最久未被服务」的。
   搅拌流是大量一次性 session（`_rr_last = -1`），因此优先被选中——victim 的链被让出来。
2. **配额上限**：`loss_cap(L) = min(kappa·L, L − max(512, 0.3L))`，`kappa=0.5` 时单会话最多被削一半，
   避免「一次被掏空」。

实测支撑：22k 预算下 RR 决定了 **84 %** 的淘汰（`victim_src: qagent=12,641 global=2,449`），
而对照臂是 100 % 全局 key。30k 时压力变小，RR 甚至不再需要牺牲全局命中率。

### 5.2 T-LRU 为什么没有保护

**插件形态（A2）** 失效原因是参数：`threshold=943` 是按会话**最终长度** 1124 标定的，但
victim 在**第 3 轮**就挂起，此时链长只有 290：

```
budget = max(L + Q − threshold, 0) = max(290 + 71 − 943, 0) = 0
⇒ 所有节点 tel-safe ⇒ 同档内按 last_access_time 排序 = 纯 LRU ⇒ 最旧的 victim 必被淘汰
```

**原生形态（A3/A4/A5）** 的现象更值得注意：

| threshold | 理论应保护 token | 22k 实测 resume_hit |
|---|---|---|
| 90 | ~271 | 6.14 |
| 200 | ~161 | 6.14 |
| 320 | ~41 | 6.14 |

**三档完全相同**，而按公式三档本应相差极大 → 22k 下 TLRU 的判定链是退化的。有两种解释，尚未区分：

- **A. 记账缺失**：被淘汰叶子的 `_tlru_history_len` 为 0 ⇒ `budget` 恒为 0 ⇒ 全部 tel-safe ⇒ LRU；
- **B. tel-safe 池不足**：tel-safe 的可淘汰量小于本轮淘汰需求（13.7k），LRU 阶段吃掉 victim。

倾向 A 的反证：30k 下原生 TLRU 能到 37.8 / 39.6 %（对照仍 6.14 %），说明它在**某些**拓扑下确实
产生了保护——若记账完全失效（恒为 LRU），30k 也应与对照相同。

**待做的一次探针**（约 10 分钟）：在 `TLRUStrategy.get_priority` 加 `SGLANG_TLRU_DEBUG=1` 门控的
采样日志（打印 `L / budget / tel_safe` 各 100 次后静默），跑一次 bench 后立即 revert。
判读：`L` 全为 0 → 解释 A；`L ≈ 290` 且 `tel_safe` 有区分 → 解释 B。

### 5.3 与论文语义的距离

| 维度 | 原生 TLRU | 本实验的插件形态 |
|---|---|---|
| 作用域 | 全局所有叶子 | 仅 QAGENT（`force_agentic` 下即全部） |
| `L` 口径 | `_tlru_history_len`（子树高水位） | 同左（插入期由插件维护） |
| 排序 | `(-1 if tel_safe else 0, last_access_time)` | 同左 |
| 会话概念 | **无** | 无（这正是它打不过 RR 的结构性原因：它不知道「谁是一条会话」） |

RR 的优势本质上来自**会话感知**；TLRU 只有「节点深度 + 时间」两个维度，无法表达
「这条会话还活着，别一次性抽干它」。本实验的结论应表述为：
**在「小流量挤出长挂起会话」这一场景下，会话感知的公平性机制优于纯节点级尾部预算。**

## 7. 局限

1. **只有 2 个 seed**（为压缩时长），配对差同号是必要条件但样本偏小；3 seed 需 +24 min。
2. **RR 的 resume 明细 CSV 已丢失**：上一轮启动原生实验前误执行 `rm -rf result`，RR 的 resume 数字
   取自当时 `summarize.py` 的输出（2-seed 中位数）。全局指标已从 tmux 回滚缓冲恢复到
   `result_recovered_22k_30k/`。若要可复算的 RR CSV，需重跑 47 min。
3. **原生 TLRU 的 22k 退化机理未定**（见 §5.2），因此「TLRU 不行」目前只能限定在
   「threshold ∈ {90, 200, 320} 且 22k 预算」这个范围内。
4. 负载是单一 agentic 数据集；混合负载（chat/struct 并存）下 `force_agentic` 会改变评分口径，
   结论不可直接外推。
5. 22k 预算下池容量小，高并发时可能出现请求级抢占（而非纯缓存淘汰），本轮未单独度量。
