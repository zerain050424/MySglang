# TTFT 报告：来源分解与各实验实测

## 1. 口径（bench 的定义，代码在 `bench_unicache.py:405-420`）

```
ttft_ms        : 客户端首 token 时延（tokenize → 排队 → prefill → 首个 decode step）
queue_time_ms  : 服务端上报的调度排队时间
prefill_ms     : forward_entry_time → prefill_finished_time，纯 prefill 计算
other          : ttft − queue − prefill（tokenize + 首 token decode + 框架开销）
```

三者是**逐请求可加**的；但不同请求的 p99 不可相加，所以下文同时给「均值分解」与「p99」。

**地板（近似全命中，recompute < 100 token）**：TTFT p50 = **53–55 ms**，prefill p50 = 36 ms。
即：一切超出 ~55 ms 的部分都是"缓存没命中"带来的代价。

## 3. TTFT 尖峰从哪来：**排队占主导**

burst 窗口的**均值分解**（逐请求可加）：

| 格 | TTFT | = queue | + prefill | + other |
|---|---|---|---|---|
| seed1 base | 1171 | **254** | 739 | 178 |
| seed1 RR | 797 | **85** | 595 | 117 |
| n_a=4 base | 1042 | **107** | 842 | 94 |
| n_a=4 RR | 543 | **2** | 465 | 76 |
| seed2 base | 1249 | **299** | 859 | 91 |
| seed2 RR | 804 | **218** | 552 | 35 |

- **prefill 只降 21–45%**（因为 RR 只保住一部分前缀，被删的部分仍要重算）；
- **排队降 66–98%**（254→85、107→2、299→218）。
- 也就是说：TTFT p99 的改善（−47%/−46%/−21%）里，**45–95% 来自队头阻塞的缓解**，不是单请求 prefill 变快。

机理：8 条会话同时回归 + 总重算量大 → 服务端把它们串行 prefill，后面的请求在队列里等。
RR 减少了 burst 内的总重算量（−30% 等），队列自然缩短；同时单条请求的 prefill 也小一些。

## 4. TTFT 与重算量近似线性

同一格内，`TTFT ≈ queue + recompute / 6.2k tok/s`：

| 数据集 | r(recompute, prefill_ms) | 等效 prefill 速率 |
|---|---|---|
| burst seed1 | 0.865 | 6,234 tok/s |
| rolling | 0.973 | 5,128 tok/s |

所以**用重算 token 数就能预测 TTFT 的尾部**，不必单独建模；反过来，TTFT p99 的改善可以还原成"少了多少 token 的 prefill"。

## 5. 反例：rolling（温和压力）下 RR 的 TTFT 更差

| arm | TTFT p50 | p99 | max | prefill p50 |
|---|---|---|---|---|
| base | **138** | 283 | 284 | 122 |
| RR κ=0.5 | 167 | **220** | **220** | 138 |
| RR κ=0.3 | 183 | 380 | 383 | 165 |

- **p99/max 更好**（283 → 220），但 **p50/p90 更差**（138 → 167/183）。
- 与 `rolling_design.md` 的结论一致：温和压力下 RR 是"削峰但抬均值"，
  TTFT 的中位数会变差，只有尾部受益。**报告 TTFT 时必须同时给 p50 和 p99**，
  只报一个会得出相反的结论。

## 6. 结论

1. 缓存未命中把 TTFT 从 **55 ms** 抬到 **1000–3000 ms**（约 20–55×）。
2. burst 场景下 TTFT 尖峰的**主因是排队（队头阻塞），不是单请求 prefill**；
   RR 的收益 45–95% 来自排队缩短。
3. 危险区（无收益）也能看出来：73k 阴性对照 TTFT 94 ms ≈ 地板，说明此时根本没在驱逐。
4. rolling 场景下 RR 出现"p99 好、p50 差"的分裂，必须成对报告。

## 7. 串行服务：回归浪潮里的 8 条请求是怎么排队的

### 7.1 一条重要的事实修正：回归并不同时

设计上 8 条空闲会话"同一轮次、同一 pause"应同时回归，实测**到达跨度 9.2–11.5 s**。
原因：每轮 `gap=6s` 之外还有一次请求时延（0.5–2 s，取决于缓存命中情况），
10 轮累计的**漂移**可达十几秒，于是"同时 pause"退化成"错开 10 s 的波"。
（这也是 `metrics.md` 里 `跨度 < 1.5 s` 守卫失败的真因，不是抖动，是系统性漂移。）

### 7.2 但 prefill 仍然是串行的

单卡 GPU 只能一批一批地做 prefill，所以 8 条请求的重算量被"排队消化"：

| arm | 到达跨度 | Σprefill | 完成跨度 | 等效并行度 | r(到达顺序, TTFT) | 串行等价(6.2k tok/s) |
|---|---|---|---|---|---|---|
| seed1 base | 11,024 ms | 5,913 ms | 13,366 ms | **0.44** | 0.53 | 6,118 ms |
| seed1 RR | 9,248 | **4,757** | 10,174 | **0.47** | 0.28 | **4,302 ms** |
| n4 base | 10,239 | 6,732 | 11,763 | 0.57 | 0.40 | 6,279 |
| n4 RR | 9,439 | **3,721** | 9,446 | 0.39 | −0.15 | **4,339** |
| seed2 base | 11,495 | 6,872 | 14,056 | 0.49 | 0.77 | 6,448 |
| seed2 RR | 11,363 | **4,413** | 13,308 | 0.33 | 0.60 | **5,267** |

- **等效并行度 = Σprefill / 完成跨度**，0.44 表示"8 条请求的 prefill 时间加起来，
  只填满了 44% 的墙钟窗口" —— 既非完全串行（1.0），也远非全并行（8.0）。
- **串行等价**：把总重算量按 6.2k tok/s 折算，base 6.1 s、RR 4.3 s。
  TTFT p99 的差值（2.8 s→1.5 s）与这个排队量的缩小同向。

### 7.3 Gantt（逐请求：红=排队，蓝=prefill）

![fig9](figs/fig9_serial.png)

读法：横轴是从第一条回归请求发出算起的墙钟；每个条形的左端 = 请求发出时刻，
红色段 = 服务端排队，蓝色段 = prefill，条形右端 = 首 token。
**base 的条形更宽、右端更靠右**（队列把后面的请求推出去了）。
RR 的 prefill 段明显更短（重算量少 30%），队列也更短。

### 7.5 结论

1. 回归浪潮**不是同时到达**（跨度 ~10 s），但 prefill 仍然是**部分串行**的（等效并行度 0.33–0.57）。
2. TTFT 的尾部 = **自己前面那几条的重算量之和 / GPU 吞吐**，所以减少总重算量直接缩短尾部。
3. RR 把 Σprefill 从 5.9–6.9 s 降到 3.7–4.8 s（−27% ~ −45%），这是 TTFT 改善的直接来源。
