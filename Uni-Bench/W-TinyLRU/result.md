## 0. 结论摘要

在 D-SLRU 负载（跨块复发模板 × 会话内私有热点 × 单轮 burst）上：

| 池容量 | LRU (A0) | 上游 SLRU (A1) | 仅 one-shot 带 (A2) | **两带 SLRU (A3)** |
|---|---|---|---|---|
| 25k | 59.0 / 51.49 | 72.3 / 45.82 | 59.5 / 51.70 | **85.8 / 50.92** |
| 50k | 72.5 / 56.31 | 77.6 / 47.07 | 72.6 / 56.40 | **91.1 / 57.02** |
| 100k | 76.5 / 58.04 | 85.7 / 49.07 | 76.4 / 58.01 | **93.3 / 58.93** |
| 150k | 78.3 / 58.71 | 88.5 / 50.85 | 78.2 / 58.70 | **93.3 / 59.45** |
| 250k | 80.9 / 59.04 | 92.4 / 54.40 | 80.7 / 59.02 | **93.3 / 59.68** |
| 400k | 86.1 / 59.30 | 93.3 / 59.04 | 86.1 / 59.30 | **93.3 / 59.68** |

单元格为「**模板完整命中率% / 总命中率%**」。要点：

1. 模板保留度在**所有**压力档上 A3 ≥ A1 ≥ A0；93.3% 是负载上限（`1 − 64/960`，见 §5.3）。
2. 总命中率 A3 ≥ A0 出现在 50k–400k 五档；**只有 25k（极端压力）落后 LRU 0.57pp**。
3. 上游 SLRU 用「会话内重复读」当频数证据，会把会话私有上下文晋升进保护段，
   导致私有命中率崩到 4.1%–43.7%（25k–250k 档）；两带 SLRU 保持 67.3%–71.2%（与 LRU 同档），
   这是「只看跨会话共享」的收益最直接的证据。

## 1. 策略设计

### 1.1 要解决的问题

前缀缓存淘汰面对三类互斥的复用信号：

| 信号 | 含义 | 典型误判 |
|---|---|---|
| **recency** | 刚被访问过 | 单轮 burst 的文档刚插完，recency 最高，但**永远不会再被读** |
| **频数（会话内）** | 同一会话反复读 | 会话私有上下文 `hit_count` 很快 ≥2，但它只服务**一个**会话，会话结束即垃圾 |
| **跨会话共享度** | 被**不同**会话命中过 | 真正值得跨请求保留的只有这一种，但它**在预热期看不到** |

三者冲突时，纯 LRU 会被 recency 带偏，上游 SLRU 会被频数带偏。

### 1.2 两带结构

```
每轮淘汰（simple_hybrid_radix_cache.evict）：
    leaves   = evictable_leaves
    one_shot = [n for n in leaves if is_one_shot(n)]
    if one_shot:  victim = min(one_shot, key=one_shot_key)   # 带0：硬优先，内部 LRU
    elif leaves:  victim = min(leaves, key=victim_key)       # 带1：全局竞争 + 改写器插话
    else: break
    _evict_one(victim)                                       # 死链级联
```

- **带 0（one-shot，硬优先）**：判定为「一次性」的节点**永远先于**其他内容被清空。
  带上不存在排序歧义——只要带非空，就不看带 1。
- **带 1（可调度 / 结构复用）**：`victim_key` 分数最低者先走，同分取 token 多者；
  已注册的改写器（`victim_overrides`）可对候选插话（返回 `None` 则保留原候选，绝不阻塞推进）。
- **不变式**：两个分支必定给 `victim` 赋值，候选**不跨轮复用**——避免同一段 KV 被二次释放。

### 1.3 一次性判定：只看「共享数 + 会话类型」，**不看 `queue_tag`**

```python
is_one_shot(node) =  账本里有该 session
                 and share_sessions(node) < share_min
                 and session_type ∈ {TRANS, STRUCT}
```

为什么必须与标签解耦：`queue_tag` 记录的是「谁创建了这段」，而共享数记录的是
「还会不会被复用」。两者会分叉——典型反例是 TRANS 会话插入的文档段后来被别的会话
反复命中：标签仍挂 `QTRANS`，但它已经是热前缀。拿标签当闸会系统性漏掉这类共享前缀，
也会错保「STRUCT 会话创建但再没人用过」的内容。

账本实现（`SlruEvictPolicy`）：

- 只在**命中**时计数（`RadixCache._record_node_hit` 在更新 `queue_tag` **之前**调用
  `on_node_hit`，保证同一次命中里账本与标签看到同一份事实）；
- `session_bloom` 按会话去重，`share_sessions = min(255, +1)`，`SESSION_SHARE_MAX=255`；
- `_split_node` 分裂时复制 `share_sessions` / `session_bloom`；
- 语义为「已被 ≥ `share_min` 个**不同**会话命中过」：`share_min=2`
  = 创建者首次重读（计 1）+ 一次外部命中（计 2）；
- 唯一旋钮 `{"slru": {"share_min": N}}`，默认 2，校验 `>= 2`；
  `is_one_shot` 与保护段 `applies_to` 读**同一个值**，不会出现「退出带 0 但进不了保护段」的空洞。

### 1.4 带内排序：LRU（本条是整轮实验最大的收获）

```python
one_shot_key(node) = (node.last_access_time,)   # 最久未访问的一次性内容先走
```

原设计是「树上**结束偏移最深**优先」（`-end_offset`，对齐上游 HeterCache 的
`evict_first` 口径），理由是序列尾部最不可能被当作前缀复用。**这条假设在本负载下是错的**，
且错得很贵：详见 §5.4 的根因分析。改成 LRU 后模板保留度 75.1% → 93.3%。

### 1.5 死链级联删除

一次性内容（如单轮会话的 response 尾巴）被删后，其祖先链往往已无其他子树，
但因「父节点不是叶子」而无法在下一轮成为候选，只能逐叶淘汰，驱逐循环为此多跑若干轮。
`_evict_one` 因此向上追溯：删除无其他子树、未上锁的祖先链，遇到根 / 分支点 / 上锁节点即停。

### 1.6 观测与仪表

`SlruEvictPolicy.stats()` 输出 `share_counted`（计入共享数的命中次数）、
`share_dedup`（同会话去重次数）、`slru_picks`（本改写器实际给出候选的次数）。
`profile_summary()` 记录每次淘汰的 `victim_src`（`one_shot` / `global` / 改写器名），
用于证明「机制确实被行使」，而不是靠指标反推。

## 2. 实验负载设计（D-SLRU）

生成器 `wtl/synth.py::build_dslru`，`--scenario dslru`。它把三条成分叠在一起，
**每条成分对准一个已知的淘汰器弱点**，从而使「谁在什么机制上更强」可归因：

| 成分 | 结构 | 对准的弱点 |
|---|---|---|
| **模板层** | 64 个变体，共享同一条 2048 token 前缀，每变体再挂 256 token 唯一尾巴 | 跨块**长间隔复发**：LRU 按 recency 会把整段模板挤出，等它下一次被用到时已重建 |
| **私有层** | 每会话一条唯一私有上下文（`lognormvariate(6.0, 0.3)`，均值 431 token），每轮完整重复 | 只有**本会话**反复读：上游 SLRU 的 `hit_count>=2` 会把它晋升进 protected |
| **burst 层** | 800 个单轮唯一文档，2048 token | 制造**真实容量压力**：插入即 recency 最高，但永不复用 |

单请求结构（顺序固定）：

```
[模板 2048 + 变体 256][私有上下文][历史输出][本轮用户 token] → 生成 256
```

调度是**决定性**的（`--no-shuffle` 配合按块铺开）：

- 模板 `v` 在 `v % 8` 块出生，出生块放 2 个会话（先把 `share_sessions` 顶到阈值），
  其后 `sessions_per_template - 2` 个会话**单调铺开**到后面的块（`birth + (j*span)//tail_slots`）；
- 每块尾部紧跟 `burst_sessions/8 = 100` 个 burst 文档；
- 于是同一模板相邻两次使用之间**一定隔着一整块 burst**，模板在 LRU 眼里必然「变冷」。

> 这里踩过两个坑，已修（commit `0a17d6c` 及前序）：
> ① 原调度 `(birth + 2k) % blocks` 会绕回出生块之前，使约 49% 的模板请求在模板**尚未创建**时到达，
> 测出来的「模板未命中」其实是「还没插过」，把 A3 系统性压低；
> ② `turns` 必须 < 5（分类器 `MULTI_TURN_MIN`），否则会话被判成 AGENTIC/CHAT，
> 节点根本不进一次性带，负载靶子失效。

### 2.1 两条 trace 的实测参数

| 参数 | `dslru3`（主用） | `dslru2`（辅助） |
|---|---|---|
| `prefix-depth` / `variant_len` | 2048 / 256 | 2048 / 256 |
| `variants` | 64 | 64 |
| `sessions-per-template` / `turns` | 5 / 3 | 5 / 3 |
| `private_mu, sigma`（实测均值） | 6.0, 0.3 → 431 token | 7.6, 0.4 → 2237 token |
| `user-len` / `output-len` | 128 / 256 | 128 / 256 |
| `blocks` | 8 | 8 |
| `burst-sessions` | 800 | 64 |
| `doc-len` | 2048 | 1024 |
| 会话数 / 请求数 | 1120 / 1760 | 384 / 576 |
| `seed` | 42（另跑 43 作噪声检查） | 42 |

### 2.2 负载规模核算（一个必须纠正的直觉错误）

模板请求长度是 `2304`，很容易得出「模板工作集 = 64 × 2304 = 147k」。**错。**
64 个变体共享**同一条** 2048 前缀，实际占用是

```
唯一存储 = 2048（共享前缀）+ 64 × 256（变体尾巴）= 18,432 token
```

即：**25k 的空池也装得下全部模板**。这解释了两件事——
A0 在 25k 上仍能拿到 59% 的模板完整率，A3 在 25k 上仍能到 85.8%；
也说明 250k / 400k 两档对模板**毫无压力**，真正被压缩的是私有上下文与 burst。
（正确的压力标尺是「私有 + burst 的工作集」，不是模板总长。）

## 3. 实验对照组设计

### 3.1 五个臂

| 臂 | policy / config | 隔离的是哪一项 |
|---|---|---|
| **A0** | `lru` | SGLang 默认基线（recency 能力边界） |
| **A1** | `slru`, `protected_threshold=2` | **上游分段 LRU**：能力上限参照（频数晋升，无准入、无 aging） |
| **A2** | `simple_hybrid`, `slru.share_min=10^6` | **只有 one-shot 带**：阈值不可达 ⇒ 保护段永不成立。与 A3 只差「保护是否存在」，用来隔离保护机制的净贡献 |
| **A3** | `simple_hybrid`, `slru.share_min=2` | **主对象**：两带 SLRU（one-shot 带 + 跨会话共享保护段 · 段内 LRU） |
| **A4** | `simple_hybrid`, `slru.share_min=3` | **剂量反应**：要 3 个会话命中过才进保护段（阈值敏感性 / 是否存在拐点） |

设计原则：`A3 − A2` 是保护的**净贡献**，`A3 − A1` 是相对上游能力的**增量**，
`A3 − A0` 是相对默认基线的**总收益**。A4 不是「更好的臂」，而是**剂量探针**：
若 `share_min` 从 2 提到 3 就崩，说明结论依赖阈值调参，机制不成立。

### 3.2 指标体系

`wtl.replay --backend real` 输出逐请求 `rows` 与 `summary`，`mx.py` 从中派生：

| 指标 | 定义 | 为什么需要它 |
|---|---|---|
| **模板完整命中率** `intact` | 模板会话的请求中 `cached_tokens >= 2304` 的比例 | 主指标：模板是唯一跨会话复用的东西，「整段还在不在」比「命中多少 token」更贴近真实可用性 |
| 模板 token 命中 `tpl_tok` | `Σ min(cached, 2304) / (n × 2304)` | 区分「整段缺失」与「只差尾部一点」 |
| 私有 token 命中 `priv_tok` | `Σ max(0, cached − 2304) / Σ(prompt − 2304)` | 反向指标：**上游 SLRU 唯一明显崩掉的地方** |
| 总命中率 `hit` | `summary.hit_pct`（全量请求，含 burst） | 防止「为了模板牺牲一切」；burst 恒为 0 命中，所以它是纯容量竞争的结果 |
| `picks` / `victim_src` | 改写器出手次数与淘汰来源 | 证明机制被行使（G2 门） |

### 3.3 控制变量

- **池容量用绝对值**（`--pool-tokens`），不用 `--pool-ratio`。后者按总工作集等比缩放，
  加 burst 就等比例加池，压力永远打不到模板上——上一轮实验就是被它耽误的。
- `--no-shuffle` + 固定 `seed`：会话到达顺序决定一切，必须可复现（否则 G1 门失败）。
- 同一份 trace 上所有臂共用相同池与 seed；`A0/A1` 不受被改文件影响，可直接与不同代码版本对照。

### 4.4 天花板

`93.3 = 1 − 64/960`：64 个模板各有一个「首次插入」请求必然未命中（此刻它还在被插入），
其余 896 个模板请求全部整段命中。**主指标已到负载上限**，在同一负载上继续提分只能靠过拟合。

## 5. 失败模式分析（本轮的诊断过程）

### 5.1 起点

带内 `-end_offset` 版本：`intact = 75.1%`（150k/250k 取最小），落后上游 17.3pp，
私有命中仅 8.9%，总命中 46.9%（低于 LRU 的 59.0%）。三项同时崩，说明问题在结构而非调参。

### 5.2 探针证据

对 `_evict_one` 插桩统计被删节点的 `(len, share_sessions)`：
被删的只有 `len=2176 share=1`（扫描文档）与 `len=384 share=1`（模板会话尾巴），
**受保护节点（2048 共享前缀 / 256 变体）一次都没被删过**。
——即「保护段本身没被破坏」，问题发生在**进入保护段之前**。

### 5.3 树结构 dump

运行结束时树里只剩 **54/64** 个变体节点，存活者 `share=4~5`（都在保护段内）。
说明约 10 个模板**从未建立起保护**：它们在预热期就被清掉，然后在新会话里重建、再被清。

### 5.4 根因

模板链 `[变体 256 + 私有 ~500]` 作为一个约 800 token 的节点在**会话创建时**插入，
此刻 `share_sessions=0`，仍属一次性，落在带 0。带 0 的排序是「结束偏移最深优先」：

```
模板链 end_offset ≈ 2850   ← 更深
扫描文档 end_offset = 2176 ← 更浅
```

于是**预热中的模板链成了第一优先牺牲品**，被自己的私有尾巴级联带走；
删除后 `share_sessions` 归零，下一会话重建，循环往复，保护永远无法建立。

上游 SLRU 不受影响：它用 `hit_count >= 2`，**创建者自己的 turn2/turn3 重读就够了**，
在模板建立后的第一个会话内即完成晋升，从不暴露在这个窗口里。
这就是「跨会话准入」相对「频数准入」的**结构代价**：证据更可信，但**来得更晚**。

### 5.5 修复与验证

带内改 LRU 后，同块内刚插/刚被读的预热链排在「早已插完、之后再未被触碰」的扫描文档之后，
预热窗口才真实存在。三个指标同向大幅改善（以 250k 档为例：`intact` 75.1→93.3（+18.2pp）、
`priv` 8.9→71.2（+62.3pp）、`hit` 46.9→59.7（+12.8pp）），
且**改动只有一行排序键**——符合「机制解释优先于调参」的判据。

### 5.6 被否掉与已删除的设计

| 设计 | 结果 | 处置 |
|---|---|---|
| 带内 `(-end_offset, last_access)` | `intact` 75.1%，`priv` 8.9% | 否掉，改 LRU |
| `on_node_inserted`（插入即记创建者，把预热窗口缩短一步） | 在 `-end_offset` 排序下 `intact` 45.8% → 70.0% | 带内改 LRU 后**完全冗余**（指标不变 93.3），已删除 |
| `pick()`（保护段内择一并接管淘汰） | `slru_picks` 在所有实验中恒为 **0** | 保留但**标记为不可达**，见 §6 |

## 6. 结论与已知局限

### 6.1 成立的部分

1. **「只看跨会话共享」比「看会话内频数」更准**：同一档池（150k）下 A3 私有命中 70.0% vs A1 26.1%，
   而模板保留度 A3 全面 ≥ A1。频数信号在这里是有害的——它奖励了单会话热点。
2. **one-shot 带 + 保护段的组合是必要的**：A2（仅带）在小池上只有 59.5%，A3 是 85.8%；
   但在 400k 上两者都 86.1% —— 保护只在**存在压力**时才有价值，符合设计预期。
3. **带内排序必须与被清对象的价值一致**：一次性内容的价值是「还没被读过的最近插入」，
   不是「序列位置最深」。这是 18pp 的教训。
4. 私有上下文命中率与 LRU 同档，说明保护段没有过度膨胀（这是 A1 的主要缺陷）。

### 6.2 已知局限

- **`pick()` 在实践中不可达**：只要请求流持续产生新的一次性内容，带 0 就永不为空，
  `elif leaves:` 分支走不到（`victim_src` 里从不出现 `global`，`slru_picks` 恒 0）。
  保护实际全靠「把节点**排除出**带 0」实现。要让 `pick()` 生效，需要「受保护工作集 > 池容量」
  的负载（本负载 18.4k ≪ 所有测试池）。
- **保护只进不出**：`share_sessions` 只增不减，没有降级/aging。长期不再复用的模板会永久占位。
- **25k 极端压力下总命中落后 LRU 0.57pp**（50.92 vs 51.49）：池只能容纳 ~10 个变体时，
  保模板与保私有上下文是零和的；该点 A3 的模板保留 85.8% vs LRU 59.0%，
  说明这是**取舍**而非缺陷，但方向需要更多负载才能判定。
- **`applies_to` 与 `is_one_shot` 不同源**：前者要求 `type == STRUCT`，后者接受 `{TRANS, STRUCT}`。
  TRANS 归属的共享节点既不上保护也不在带内。当前未触发（带 0 非空时 `pick` 不被调用），
  属潜在 bug。
- **样本规模**：单一合成负载族（D-SLRU）+ 两个 seed + 真实 trace 未覆盖；
  结论的可迁移性仍需 ShareGPT / 真实 agentic trace 验证。

# 0) 生成 trace（实验机，需真 sglang）
