# tail-stress：专门暴露「LRU 整链淘汰 → P90 TTFT 劣化」的负载

> 【长尾优化专题 · 负载设计】暴露 LRU 整链击穿导致 P90 TTFT 劣化的基准负载构造方法

## 一、实验环境

| 项 | 值 |
|---|---|
| 仿真器 | `Simulator.run_engine`，`EngineConfig(schedule_policy="fcfs")`、`max_prefill_tokens=16384`、chunked prefill 关 |
| page / 容量 | page=8、**cap=198,000** token |
| 服务模型 | `prefill_base_s=0`、`prefill_tokens_per_s=8319.6`（`Uni-Bench/result/tailshot/calib_lru.json`）、decode 40 tok/s |
| TTFT 口径 | `TTFT = (派发时刻 − 到达时刻) + (prompt_len − hit) / 8319.6`；到达时刻由 `sim.engine._Queued.due` 抓取，1700 个请求全部配对 |
| 生成器 | `Heter-Bench/mixexp/tools/build_tail_stress.py` |
| 随机性 | token 内容 `random.Random(7)`、模板 `Random(99)`；会话起点 Poisson（seed 42/43/44）；仿真 seed=0 |

## 二、负载设计

三类会话，各自承担一个变量：

| 类 | 规模 | 轮数 | 轮间空窗 | prompt 形态 | 作用 |
|---|---|---|---|---|---|
| `hot` | 60 会话 | 8 | **3s** | 800 → ~5k，逐轮 +600 | 持续刷新 LRU 的 recency，把"新"这个信号占住 |
| `warm` | 40 会话 | 8 | **45s** | 1500 → **~12k，完全私有** | 被暴露的对象：慢回来、链路长、且会话间不共享 |
| `cold` | 900 会话 | 1 | — | 7,000 共享模板 + 1,000 私有 | 提供容量压力，但命中模板后 TTFT 只要 ~130ms |

### 三条设计原则（每条对应一个被测机制）

1. **让 recency 与复用价值背离**。LRU 只有"最近访问"一个信号。hot 的 3s 间隔让它
   永远比 warm 新，而 warm 45s 的 recency 立刻变旧 —— 于是 LRU 会**系统性地**、
   而不是偶发地优先淘汰 warm。容量周转尺度（≈198k ÷ 写入速率）被刻意放在
   3s 与 45s 之间。
2. **代价必须是"整链"而不是"尾巴"**。warm 的 12k 前缀完全私有 ⇒ 一旦被淘汰就是
   `hit=0`、`need≈12k`、单次 TTFT≈1.4s。若共享前缀足够长，命中会被共享部分兜住，
   缺陷就被掩盖了（这正是真实 chat 负载里 P90 只差几 ms 的原因）。
3. **缺陷要落在 P90 上**。warm 请求占比 18.8%（>10%），P90 正好落在 warm 区间；
   若 warm 只有 1%~2%，抬高的只是 P99 的离群点。

### 自检三条（换参数时必须复验）

| 判据 | 本配置实测 | 含义 |
|---|---|---|
| `cold` 的 p90 ≤ 300ms | **230ms** | 没有排队积压，P90 不是拥塞顶上去的 |
| `warm` 整链丢失率 ≥ 50% | **52.2%** | 缺陷确实被触发 |
| LRU/OPT 的 P90 ≥ 3× | **5.0×** | 有足够可回收空间，值得当 benchmark |

### 调参旋钮与已观测的边界

- **cap 调小到 120k**：整链丢失升到 96.9%，但 FCFS 队列开始积压，P90 从 920ms 跳到
  **5232ms**，`cold` 的 p90 也变得 4219ms —— 此时测的是拥塞而不是淘汰粒度，隔离性丢失。
- **warm_gap 从 45s 调到 70s**：整链丢失 52%→80%，但 cold 的 p90 升到 824ms，同样开始混入排队。
- **cold 模板从 5k 提到 7k**：cold 更便宜（TTFT 129→135ms 几乎不变），但同样维持住了压力。

结论：**cap=198k + warm_gap=45s 是"缺陷显著"且"无拥塞污染"的平衡点**。

## 三、结果

| 臂 | 总体 hit | TTFT p50 | **p90** | p95 | p99 |
|---|---|---|---|---|---|
| LRU | 77.63% | 135ms | **920ms** | 1719ms | 4590ms |
| heter_cache（TTL 300） | 73.70% | 137ms | **1620ms** | 2990ms | 5879ms |
| OPT（Belady 上界） | 84.84% | 133ms | **184ms** | 215ms | 524ms |

分类明细：

| 类 | 占比 | LRU hit / 整链 / p90 | heter hit / 整链 / p90 | OPT hit / 整链 / p90 |
|---|---|---|---|---|
| hot | 28.2% | 0.845 / 12.5% / 232ms | 0.803 / 16.2% / 661ms | 0.845 / 12.5% / 118ms |
| **warm** | **18.8%** | **0.426 / 52.2% / 2783ms** | **0.257 / 74.7% / 4260ms** | **0.785 / 14.1% / 244ms** |
| cold | 52.9% | 0.868 / 0.8% / 230ms | 0.868 / 0.8% / 993ms | 0.868 / 0.8% / 157ms |

（`hot` 的 12.5% 整链丢失 = 8 轮里的第 1 轮，天然 hit=0，属基线而非缺陷）

## 四、对比分析

1. **P90 的 736ms 差距（920 → 184ms，5.0×）完全由 warm 的整链丢失解释**：
   warm 的整链丢失率 52.2% → 14.1%，hit 0.426 → 0.785，p90 2783 → 244ms。
   hot 与 cold 在两臂之间的 p90 都在 230ms 上下，说明这个差距既不是排队积压，
   也不是"没有复用机会的流量"造成的。
2. **LRU 的错是系统性的**：warm 每一轮回来几乎都会被横扫（8 轮里 4 轮 hit=0），
   而不是偶发挑错。这正是"recency ≠ 复用概率"的直接后果——hot 的持续到达让
   warm 在 recency 上永远是"最旧的那批"。
3. **heter_cache 在这条负载上比 LRU 更差**（P90 1620ms vs 920ms，warm 整链 74.7%）。
   one-shot 带的判据（未重读 + 会话搁置 >20s + 共享数 <2）几乎正好命中 warm 的画像：
   私有、轮间 45s、且第一次命中前 `reuse_count` 一直是 0 —— 于是它淘汰得比 LRU 还狠。
   这说明现有策略的"陈旧度"判据与"会话是否还会回来"是两件事。
4. **这条负载适合当回归靶子**：任何针对"整链丢失"的改动（例如淘汰排序里加
   「本次淘汰会不会让某会话剩余路径变空」的惩罚项）都应该在这条负载上看到
   P90 下降、而**总 miss token 基本不变**；若总 miss 变了，说明改的是"淘汰量"而不是
   "淘汰形状"，就不是这个靶子要测的东西。
5. **局限**：hot/cold/warm 的三段式是人工构造的极端画像，绝对数值不能外推到线上；
   它能回答的是"哪些机制会在这类负载上放大 P90"，不能回答"线上 P90 是多少"。
   OPT 的时间轴固定点迭代 4 轮后残差 0/1700，上界可信。
